# Testing Strategy

> Status: `draft`
> Related: `03-engineering/CONVENTIONS.md`, `AGENTS.md`
> Last updated: _YYYY-MM-DD_

Untested code is unfinished code. A feature is `completed` only when the tests required below exist and pass.

---

## 1. Test Pyramid

| Level | Purpose | Scope | Target proportion | Runs on |
|-------|---------|-------|-------------------|----------|
| Unit | Behavior of a single function/module in isolation | no I/O, all collaborators mocked | ~70% | every commit |
| Integration | Interaction across real boundaries: DB, queue, HTTP, filesystem | real dependency, isolated container | ~25% | every commit |
| E2E | User-visible journeys through the deployed stack | full stack | ~5% | pre-release, main branch |

Ratio is a guideline, not a target to game. Coverage percentage is **not** a quality metric; behavior coverage is. 100% line coverage with no assertion on an error path is worse than 70% with meaningful assertions.

---

## 2. Unit Testing Standards

- **Test behavior, not implementation.** Do not assert on private fields, call order, or internal call counts.
- One behavior per test; the test name states the behavior (`it("rejects an expired token")`).
- **Arrange / Act / Assert** structure with blank lines separating the three phases.
- Every branch introduced by the feature has a test: happy path, boundary, and failure path.
- No network, filesystem, clock, or randomness in unit tests. Inject dependencies; freeze time; seed randomness.
- **AAA** is mandatory. Comments explaining the assertion are a smell — name the test instead.
- Prefer table-driven tests for input/output matrices.

```
it("...", () => {
  // Arrange

  // Act

  // Assert
});
```

## 3. Integration Testing

Integration tests cover the boundaries where design documents make promises.

| Boundary | Must be tested for | Example file |
|----------|-------------------|--------------|
| API ↔ client | request validation, auth/authz, status codes, error envelope | `tests/api/*.int.test.ts` |
| Service ↔ database | queries, transactions, constraints, migrations | `tests/db/*.int.test.ts` |
| Service ↔ queue/event | publish format, idempotency, retry behavior, DLQ | `tests/events/*.int.test.ts` |
| Service ↔ third party | timeout, retry, partial failure, contract shape | `tests/integrations/*.int.test.ts` |

Rules:

- Tests run against the **real** dependency in an isolated environment (container or ephemeral database), never a shared mutable one.
- Each test starts from a known state and is independent — order must not matter.
- Wrap the test in a transaction and roll back, or recreate state per test.
- Assert on the **observable effect** (rows written, events emitted, HTTP response), not on internal call sequences.
- Contract tests run against a recorded or live third-party contract to catch upstream breakage.

---

## 4. E2E Testing

- Cover only critical user journeys — the ones whose failure means the product is broken.
- Each E2E test maps to a numbered user story or acceptance criterion.
- Selectors use `data-testid` or accessible roles/names. Never depend on CSS class names or DOM position.
- No fixed `sleep`. Wait for a condition.
- E2E failures must be reproducible locally with one command.
- Keep the E2E suite small enough to run in minutes; a slow suite is a skipped suite.

---

## 5. Test Data Management

- **No real user data in any environment.** Synthetic data only.
- Factory/builders create valid objects by default; tests override only the fields they care about.
- Fixtures for third-party APIs are recorded and scrubbed of credentials.
- Tests needing "now" use a fixed clock; tests needing randomness use a seeded generator.
- Bulk data for performance tests is generated by a script under `scripts/`, never committed as large files.
- A `seed` script must exist and be documented in `02-design/DATA_MODEL.md` section 7.

## 6. CI/CD Integration

| Stage | Command | Gate |
|-------|---------|------|
| Install | `pnpm install --frozen-lockfile` | fails on lockfile drift |
| Lint | `pnpm lint` | blocking |
| Format check | `pnpm format:check` | blocking |
| Typecheck | `pnpm typecheck` | blocking |
| Unit + integration tests | `pnpm test` | blocking |
| Build | `pnpm build` | blocking |
| E2E (main/pre-release) | `pnpm test:e2e` | blocking |
| Dependency scan | `pnpm audit` / scanner | blocking on high/critical |
| Secret scan | pre-commit + CI | blocking |

Rules:

- A failing test is fixed or reported. It is never deleted, skipped, or weakened to go green (see `AGENTS.md` rule 6).
- Flaky tests are a bug: quarantine and fix within the same cycle, never leave permanently skipped.
- Coverage is reported per module; a drop below the agreed floor is reviewed, not automatically blocked.
- Branch protection requires all blocking stages to pass on the pull request before merge.
